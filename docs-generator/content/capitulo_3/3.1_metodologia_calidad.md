# 3.1 Metodología PSP y Estandarización

Humphrey (2005) diseñó el Personal Software Process
(PSP) para que un ingeniero individual alcance
disciplina de calidad equiparable a la de equipos
regidos por CMMI. A diferencia de Scrum o XP, PSP
no exige roles ni ceremonias grupales: prescribe
que el propio desarrollador mida, planifique,
revise y especifique su trabajo con rigor.

Poetry adopta PSP como columna metodológica. Cada
nivel del proceso se corresponde con artefactos
concretos del proyecto:

- **PSP0 — Proceso base.** Registro de cambios
mediante Git con convenciones de commit estrictas
y estructura DDD prescrita desde el inicio.
- **PSP1 — Planificación.** Blueprints JSON definen
la estructura obligatoria de cada módulo antes de
codificar la primera línea.
- **PSP2 — Revisión de calidad.** Trece gates
automatizados validan encabezados, longitud,
internacionalización y formato en cada commit.
- **PSP2.1 — Especificación de diseño.** Contratos
OpenAPI, blueprints de arquitectura y catálogo de
componentes documentan las decisiones de diseño.

### 3.1.1 Pipeline CI/CD Local y Reglas de Calidad

Las reglas se codifican en el archivo
`code-standards.config.json`. La regla 60/60 fuerza
sesenta líneas por archivo y sesenta caracteres por
línea, obligando a la segregación que Martin (2017)
prescribe con SRP. ESLint, Checkstyle y TypeScript
completan la barrera automatizada que Sommerville
(2016) denomina «integración continua defensiva».
